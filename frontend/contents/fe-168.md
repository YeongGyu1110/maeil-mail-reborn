**Vite** 는 개발 서버와 프로덕션 빌드를 함께 제공하는 프론트엔드 빌드 도구입니다. webpack과 가장 큰 차이는 **개발 서버가 코드를 다루는 방식**입니다.

### webpack의 개발 서버: 번들 기반
webpack은 개발 서버를 시작할 때 **진입점부터 모든 모듈을 따라가며 하나의 번들로 묶은 뒤** 서버를 띄웁니다. 그래서 프로젝트가 커질수록 서버 시작 시간이 길어지고, 파일을 수정하면 관련 번들을 다시 만들어야 해서 HMR(Hot Module Replacement)도 점점 느려집니다.

### Vite의 개발 서버: 네이티브 ESM 기반
최신 브라우저는 `<script type="module">`과 `import` 문을 직접 이해합니다. Vite는 이를 이용해 **개발 중에는 번들링을 하지 않습니다.**

- 서버는 거의 즉시 시작하고, 브라우저가 `import`로 **실제로 요청한 파일만 그때그때 변환**해서 전달합니다. 지금 보고 있지 않은 페이지의 코드는 변환하지 않습니다.
- 파일을 수정하면 **바뀐 모듈과 그 경계만 교체**하므로, 프로젝트 크기와 상관없이 HMR이 빠르게 유지됩니다.
- 변경이 거의 없는 소스 코드는 `304 Not Modified`로, 버전이 고정된 의존성은 강한 캐시 헤더로 브라우저 캐시를 활용합니다.

## Vite는 node_modules의 의존성도 그대로 브라우저에 보내나요? 🤔

아닙니다. 의존성은 **사전 번들링(Dependency Pre-Bundling)** 을 합니다. 그 이유는 두 가지입니다.

1. **CommonJS 변환**: npm 패키지 중에는 아직 CommonJS나 UMD 형식으로 배포되는 것이 많습니다. 브라우저는 ESM만 이해하므로 ESM으로 변환해야 합니다.
2. **요청 수 줄이기**: `lodash-es`처럼 내부 모듈이 수백 개인 패키지를 그대로 보내면, 브라우저가 수백 개의 HTTP 요청을 보내 오히려 느려집니다. 그래서 패키지 하나를 하나의 모듈로 미리 묶습니다.

이 사전 번들링에는 Go로 작성된 매우 빠른 번들러인 **esbuild** 를 사용하고, 결과는 `node_modules/.vite`에 캐시해 다음 실행부터 재사용합니다. (최신 버전에서는 Rust로 작성된 Rolldown으로 전환되고 있습니다.)

## 개발할 때 번들링을 안 한다면, 프로덕션 빌드도 번들링을 안 하나요? 🧐

프로덕션에서는 **번들링을 합니다.** 개발 환경은 로컬 서버라 요청이 많아도 빠르지만, 실제 배포 환경에서 번들링하지 않은 수많은 모듈을 내려받으면 네트워크 왕복이 많아져 느려지기 때문입니다. Vite는 프로덕션 빌드에 Rollup 기반의 번들러를 사용해 **트리 쉐이킹, 코드 스플리팅, 청크 최적화, 압축**을 수행합니다.

이처럼 개발 환경과 프로덕션 환경의 처리 방식이 다르기 때문에, 드물게 **개발 서버에서는 동작하는데 빌드 결과에서는 동작하지 않는** 차이가 생길 수 있습니다. 그래서 배포 전에 `vite build` 후 `vite preview`로 빌드 결과를 확인하는 것이 좋습니다.

## 그렇다면 webpack은 더 이상 쓰지 않나요?

새 프로젝트에서는 Vite가 많이 선택되지만, webpack은 오랜 기간 쌓인 **풍부한 로더와 플러그인 생태계, 세밀한 설정, Module Federation** 같은 기능 덕분에 대규모 레거시 프로젝트에서 여전히 많이 사용됩니다. 또한 Rspack처럼 webpack과 호환되면서 Rust로 성능을 높인 도구도 등장해, 기존 webpack 설정을 유지하면서 속도를 개선하는 선택지도 있습니다.
