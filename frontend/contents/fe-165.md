세 테스트는 **검증하는 범위**가 다릅니다.

- **단위 테스트(Unit Test)**: 함수, 훅, 작은 컴포넌트처럼 **가장 작은 단위를 다른 것과 분리해서** 검증합니다. 빠르고 실패 원인을 찾기 쉽지만, 여러 단위가 함께 동작할 때의 문제는 잡지 못합니다.
- **통합 테스트(Integration Test)**: **여러 단위가 함께 동작하는 흐름**을 검증합니다. 프론트엔드에서는 보통 페이지나 기능 단위 컴포넌트를 렌더링하고, 사용자처럼 입력하고 클릭했을 때 결과 화면이 올바른지 확인합니다. 네트워크 요청은 모킹합니다.
- **E2E 테스트(End-to-End Test)**: **실제 브라우저에서 실제 서버까지 포함한 전체 흐름**을 사용자 시나리오대로 검증합니다. 가장 실제와 가깝지만 느리고, 네트워크나 데이터 상태에 따라 결과가 흔들리기(flaky) 쉽습니다.

| | 단위 | 통합 | E2E |
|---|---|---|---|
| 범위 | 함수, 훅, 작은 컴포넌트 | 여러 컴포넌트와 상태 흐름 | 브라우저부터 서버까지 전체 |
| 속도 | 매우 빠름 | 빠름 | 느림 |
| 신뢰도 | 낮음 | 높음 | 매우 높음 |
| 대표 도구 | Vitest, Jest | Vitest + React Testing Library + MSW | Playwright, Cypress |

## 프론트엔드에서는 어떤 테스트에 가장 많이 투자해야 할까요? 🤔

백엔드에서는 단위 테스트를 가장 많이 작성하는 **테스트 피라미드**가 널리 알려져 있습니다. 하지만 프론트엔드에서는 **통합 테스트의 비중을 가장 크게 두는 테스팅 트로피(Testing Trophy)** 모델이 자주 언급됩니다.

UI 코드는 컴포넌트, 상태, 이벤트, 라우팅이 함께 맞물려 동작해야 의미가 있습니다. 컴포넌트 하나하나를 단위 테스트로 검증해도 조합했을 때 깨질 수 있고, 내부 구현을 자세히 검증하는 단위 테스트는 리팩터링할 때마다 깨지기 쉽습니다. 그래서 다음처럼 역할을 나누는 경우가 많습니다.

- **정적 분석**: TypeScript와 ESLint로 오타, 타입 오류 같은 문제를 가장 먼저 잡습니다.
- **단위 테스트**: 날짜 계산, 가격 포맷팅, 유효성 검사처럼 **분기가 많은 순수 로직**에 집중합니다.
- **통합 테스트**: 로그인 폼, 장바구니처럼 **사용자 관점의 기능 흐름**을 가장 많이 작성합니다.
- **E2E 테스트**: 회원가입, 결제처럼 **절대 깨지면 안 되는 핵심 시나리오** 몇 개만 작성합니다.

## 테스트가 구현 세부 사항에 의존하면 어떤 문제가 생기나요? 🧐

컴포넌트의 state 값이나 내부 함수 호출 횟수처럼 **사용자에게 보이지 않는 구현을 검증**하면, 동작은 그대로인데 내부 구조만 바꿔도 테스트가 실패합니다. 반대로 실제 버그가 있어도 내부 값만 맞으면 테스트가 통과할 수 있습니다. 이런 테스트는 리팩터링을 방해하고 신뢰도도 낮습니다.

그래서 프론트엔드 테스트는 "버튼을 누르면 목록에 항목이 추가된다"처럼 **사용자가 관찰할 수 있는 결과**를 검증하는 것이 좋습니다. React Testing Library가 role, label, text로 요소를 찾도록 권장하는 것도 이 때문입니다.
