**타입 좁히기(Type Narrowing)** 는 유니온처럼 넓은 타입을 가진 값을, **조건문 등을 통해 특정 블록 안에서 더 구체적인 타입으로 좁혀 나가는 것**입니다. TypeScript는 코드의 흐름을 분석(Control Flow Analysis)해서, 조건을 통과한 블록 안에서는 값의 타입을 자동으로 좁혀 줍니다.

```ts
function format(value: string | number) {
  if (typeof value === 'string') {
    return value.toUpperCase(); // string
  }
  return value.toFixed(2);      // number
}
```

## 타입을 좁히는 방법에는 어떤 것들이 있나요? 🤔

- **`typeof`**: 원시 타입을 구분합니다. 단, `typeof null`은 `'object'`이므로 주의해야 합니다.
- **`instanceof`**: 클래스 인스턴스를 구분합니다. (`error instanceof TypeError`)
- **`in` 연산자**: 특정 프로퍼티가 있는지로 객체 타입을 구분합니다. (`'swim' in animal`)
- **동등 비교와 truthy 검사**: `if (value !== null)`, `if (value)`로 `null`과 `undefined`를 제거합니다.
- **판별 유니온(Discriminated Union)**: 공통 리터럴 프로퍼티로 타입을 구분합니다.
- **사용자 정의 타입 가드**: 반환 타입에 `value is Type`을 적은 함수를 만듭니다.
- **단언 함수(Assertion Function)**: `asserts value is Type`을 반환 타입으로 적으면, 함수가 에러 없이 끝난 이후의 코드에서 타입이 좁혀집니다.

```ts
function isUser(value: unknown): value is User {
  return typeof value === 'object' && value !== null && 'id' in value;
}

const data: unknown = await res.json();
if (isUser(data)) {
  data.id; // User
}
```

사용자 정의 타입 가드는 **함수 안의 검사 로직이 정확한지 TypeScript가 검증하지 않는다**는 점을 주의해야 합니다. 검사가 잘못되면 타입과 실제 값이 달라질 수 있으므로, 외부 데이터 검증이 중요하다면 Zod 같은 스키마 검증 라이브러리를 사용하기도 합니다.

## 판별 유니온은 어떻게 활용하나요? 🧐

각 타입에 `type`, `status`처럼 **같은 이름의 리터럴 프로퍼티**를 두고, 그 값으로 분기하는 패턴입니다. API 요청 상태나 리듀서의 액션 타입을 표현할 때 자주 사용합니다.

```ts
type RequestState =
  | { status: 'loading' }
  | { status: 'success'; data: User[] }
  | { status: 'error'; error: Error };

function render(state: RequestState) {
  switch (state.status) {
    case 'loading':
      return '로딩 중...';
    case 'success':
      return state.data.length;  // data에 안전하게 접근
    case 'error':
      return state.error.message;
    default: {
      const exhaustive: never = state; // 처리하지 않은 경우가 있으면 컴파일 에러
      return exhaustive;
    }
  }
}
```

`data?: User[]; error?: Error`처럼 선택적 프로퍼티로 표현하면 "로딩 중인데 데이터도 있는" 불가능한 상태를 막을 수 없습니다. 판별 유니온을 쓰면 **불가능한 상태를 타입으로 표현할 수 없게** 만들 수 있고, `default`에서 `never`에 할당하는 **완전성 검사(exhaustiveness check)** 로 새 상태가 추가되었을 때 처리 누락을 컴파일 단계에서 잡을 수 있습니다.
