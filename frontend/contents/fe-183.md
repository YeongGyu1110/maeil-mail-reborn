프론트엔드 코드는 **사용자의 브라우저에서 실행**됩니다. 그래서 서버 로그처럼 에러가 우리 쪽에 남지 않고, 사용자가 신고하지 않으면 에러가 났는지조차 알 수 없습니다. 게다가 브라우저 종류, 기기, 네트워크, 확장 프로그램처럼 개발 환경에서 재현하기 어려운 변수가 많습니다. 그래서 **사용자 환경에서 발생한 에러를 자동으로 수집하고 분석하는 에러 모니터링**이 필요합니다.

대표적인 도구인 **Sentry** 를 기준으로 보면, 에러 모니터링은 다음과 같은 정보를 함께 수집합니다.

- **스택 트레이스**: 에러가 발생한 코드 위치 (소스맵으로 원본 코드 위치로 변환)
- **환경 정보**: 브라우저, OS, 기기, 페이지 URL, 배포 버전(release)
- **사용자 정보**: 어떤 사용자에게 몇 번 발생했는지 (개인정보는 마스킹)
- **브레드크럼(Breadcrumbs)**: 에러 직전의 클릭, 페이지 이동, 네트워크 요청, 콘솔 로그 같은 사용자 행동 기록
- **세션 리플레이**: 에러가 발생하기까지의 화면을 재구성한 영상

같은 원인의 에러는 하나의 이슈로 묶어 **발생 횟수와 영향받은 사용자 수**를 보여주므로, 어떤 에러부터 고칠지 우선순위를 정할 수 있습니다.

## 프론트엔드에서 에러는 어떻게 수집하나요? 🤔

에러가 발생하는 경로마다 수집 방법이 다릅니다.

- **처리되지 않은 에러**: `window.addEventListener('error', ...)`로 잡습니다.
- **처리되지 않은 Promise 거부**: `window.addEventListener('unhandledrejection', ...)`로 잡습니다.
- **React 렌더링 에러**: Error Boundary의 `componentDidCatch`에서 수집하고, 사용자에게는 대체 화면을 보여줍니다. React 19의 `createRoot`에는 `onCaughtError`, `onUncaughtError` 옵션도 있습니다.
- **직접 처리한 에러**: `try...catch`나 API 에러 처리 로직에서 잡은 에러는 자동으로 수집되지 않으므로, `Sentry.captureException(error)`처럼 직접 보내야 합니다.

Sentry SDK는 위의 전역 핸들러 등록을 자동으로 해 줍니다. 다만 다른 출처(CDN)에서 불러온 스크립트의 에러는 브라우저가 보안상 `Script error.`로만 알려주므로, `<script crossorigin>`과 서버의 CORS 헤더를 설정해야 상세 정보를 얻을 수 있습니다.

## 에러 모니터링을 운영할 때 주의할 점은 무엇인가요? 🧐

- **노이즈 관리**: 브라우저 확장 프로그램, 봇, 네트워크 끊김 같은 우리가 고칠 수 없는 에러까지 모두 수집하면 중요한 에러가 묻힙니다. 무시할 에러를 필터링하고, 이슈를 담당자에게 배정하는 규칙을 둡니다.
- **알림 피로 방지**: 모든 에러마다 알림을 보내면 결국 아무도 보지 않게 됩니다. 새로운 이슈나 급증한 이슈, 핵심 기능(결제 등)의 에러만 알림을 보냅니다.
- **샘플링과 비용**: 트래픽이 많으면 모든 이벤트를 보내는 비용이 크므로, 성능 추적이나 세션 리플레이는 일부만 샘플링합니다.
- **개인정보 보호**: 요청 본문, 입력값, 화면 녹화에 개인정보가 포함되지 않도록 마스킹합니다.
- **배포와 연결**: 배포 버전을 함께 기록하면 "이번 배포 이후 새로 생긴 에러"를 바로 확인하고 롤백 여부를 판단할 수 있습니다.
