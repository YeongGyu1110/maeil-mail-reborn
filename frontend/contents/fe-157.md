비동기 요청에서 **경쟁 상태(Race Condition)** 란, 여러 요청이 동시에 진행될 때 **응답이 요청한 순서와 다르게 도착해 잘못된 결과가 화면에 반영되는 문제**입니다.

예를 들어 검색창에 `r`, `re`, `rea`를 빠르게 입력하면 세 번의 요청이 나갑니다. 이때 `rea` 응답이 먼저 오고 `re` 응답이 나중에 도착하면, 사용자는 `rea`를 입력했는데 화면에는 `re`의 검색 결과가 남습니다. 상세 페이지에서 ID를 빠르게 바꿀 때도 같은 문제가 생깁니다.

이 문제는 **이전 요청을 취소하거나, 이전 요청의 응답을 무시**하는 방식으로 해결합니다.

### 1. 응답 무시하기
`useEffect`의 클린업 함수에서 플래그를 바꿔, 이미 지나간 요청의 응답은 상태에 반영하지 않습니다.

```jsx
useEffect(() => {
  let ignore = false;
  fetchResults(query).then((data) => {
    if (!ignore) setResults(data);
  });
  return () => { ignore = true; };
}, [query]);
```

### 2. AbortController로 요청 취소하기
`AbortController`는 **진행 중인 비동기 작업을 취소할 수 있게 해 주는 Web API** 입니다. `fetch`에 `signal`을 넘긴 뒤 `abort()`를 호출하면 요청이 중단되고, `fetch`가 반환한 Promise는 `name`이 `'AbortError'`인 에러로 reject됩니다.

```jsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setResults)
    .catch((error) => {
      if (error.name === 'AbortError') return; // 취소된 요청은 무시
      setError(error);
    });

  return () => controller.abort();
}, [query]);
```

응답을 무시하는 방식과 달리, **실제 네트워크 요청까지 중단**해서 불필요한 데이터 전송과 처리 비용도 줄일 수 있습니다.

## AbortController는 요청 취소 외에 어디에 활용할 수 있나요? 🤔

- **타임아웃**: `AbortSignal.timeout(5000)`을 `signal`로 넘기면 5초가 지나면 요청이 자동으로 중단됩니다. 이때 에러 이름은 `'TimeoutError'`입니다.
- **이벤트 리스너 일괄 해제**: `addEventListener`의 옵션으로 `signal`을 넘기면, `abort()` 한 번으로 등록한 리스너들을 한꺼번에 제거할 수 있습니다.
- **여러 작업 함께 취소**: `AbortSignal.any([...])`로 여러 signal을 묶어 하나라도 취소되면 함께 중단되게 할 수 있습니다.

## 서버로 이미 전송된 요청을 취소하면 서버 작업도 취소되나요? 🧐

아닙니다. `abort()`는 **클라이언트가 응답을 더 기다리지 않고 연결을 끊는 것**일 뿐입니다. 서버가 이미 요청을 받아 처리하고 있다면 작업은 계속될 수 있습니다. 그래서 결제나 주문처럼 상태를 바꾸는 POST 요청은 취소로 문제를 해결하기보다 **중복 제출 방지와 멱등성 키** 처럼 서버와 함께 설계해야 합니다.

참고로 TanStack Query 같은 데이터 패칭 라이브러리는 쿼리 키가 바뀌면 이전 응답을 자동으로 무시하고, 쿼리 함수에 `signal`을 넘겨 요청 취소도 지원합니다.
