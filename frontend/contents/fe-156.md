**OAuth 2.0** 은 사용자가 **비밀번호를 넘겨주지 않고도, 제3자 애플리케이션이 다른 서비스의 자원에 제한적으로 접근하도록 권한을 위임**하는 표준 프레임워크입니다. "구글로 로그인", "카카오로 로그인" 같은 소셜 로그인이 대표적인 활용 예입니다.

OAuth 2.0에는 네 가지 역할이 있습니다.

- **Resource Owner**: 자원의 주인, 즉 사용자입니다.
- **Client**: 사용자의 자원에 접근하려는 애플리케이션입니다. (우리 서비스)
- **Authorization Server**: 사용자를 인증하고 Access Token을 발급하는 서버입니다. (구글, 카카오의 인증 서버)
- **Resource Server**: 실제 자원을 가진 API 서버입니다. Access Token을 확인하고 자원을 내어줍니다.

## Authorization Code 방식의 흐름을 설명해주세요. 🤔

웹 애플리케이션에서 가장 많이 사용하는 방식입니다.

1. 사용자가 "구글로 로그인"을 누르면, Client는 사용자를 Authorization Server의 인가 페이지로 이동시킵니다. 이때 `client_id`, `redirect_uri`, 요청할 권한 범위인 `scope`, 그리고 임의의 값인 `state`를 함께 보냅니다.
2. 사용자가 로그인하고 권한 제공에 동의합니다.
3. Authorization Server는 `redirect_uri`로 사용자를 돌려보내면서 **짧은 수명의 Authorization Code** 를 쿼리 파라미터로 전달합니다.
4. Client의 **서버**가 Authorization Code와 `client_secret`을 Authorization Server에 보내 **Access Token(과 Refresh Token)으로 교환**합니다.
5. Client는 Access Token으로 Resource Server의 API를 호출합니다.

토큰을 브라우저 주소창에 직접 노출하지 않고 **한 번 쓰고 버리는 Code를 서버 간 통신으로 교환**한다는 점이 핵심입니다. 이때 `state` 값은 돌아온 응답이 내가 시작한 요청이 맞는지 확인해 CSRF를 막는 용도입니다.

## SPA나 모바일 앱처럼 client_secret을 안전하게 보관할 수 없는 경우는 어떻게 하나요? 🧐

브라우저나 앱에 포함된 코드는 누구나 볼 수 있어서 `client_secret`을 숨길 수 없습니다. 이런 **public client** 는 **PKCE(Proof Key for Code Exchange)** 를 사용한 Authorization Code 방식을 사용합니다.

1. Client가 임의의 문자열 `code_verifier`를 만들고, 이를 SHA-256으로 해시한 `code_challenge`를 인가 요청에 함께 보냅니다.
2. 토큰 교환 시 원본 `code_verifier`를 보내면, Authorization Server가 해시해서 처음 받은 `code_challenge`와 일치하는지 확인합니다.

이렇게 하면 중간에 Authorization Code가 탈취되더라도 `code_verifier`를 모르는 공격자는 토큰을 받을 수 없습니다. 과거에는 SPA에서 토큰을 URL로 바로 받는 Implicit 방식을 썼지만, 토큰 노출 위험 때문에 현재는 **권장되지 않으며** PKCE를 사용하는 것이 표준입니다.

## OAuth 2.0과 OpenID Connect(OIDC)는 어떤 차이가 있나요?

OAuth 2.0은 **인가(무엇에 접근할 수 있는가)** 를 위한 프로토콜이라, Access Token만으로는 "이 사용자가 누구인지"를 표준화된 방식으로 알기 어렵습니다. **OIDC** 는 OAuth 2.0 위에 **인증(누구인가)** 계층을 더한 표준으로, 사용자 정보를 담은 JWT 형식의 **ID Token** 을 함께 발급합니다. 소셜 로그인은 보통 OIDC를 기반으로 동작합니다.
