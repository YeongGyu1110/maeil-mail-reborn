**ESLint** 와 **Prettier** 는 모두 코드를 일관되게 유지하기 위한 도구지만, 목적이 다릅니다.

### ESLint: 코드 품질 검사 도구(Linter)
코드를 실행하지 않고 분석해 **버그 가능성이 있는 패턴이나 팀 규칙 위반을 찾아내는** 정적 분석 도구입니다. 예를 들어 사용하지 않는 변수, 선언하지 않은 변수 사용, `useEffect` 의존성 배열 누락, `==` 사용 같은 문제를 잡습니다. 규칙마다 경고 수준을 정할 수 있고, 일부는 자동으로 고칠 수 있으며, 플러그인으로 React, TypeScript, 접근성 등 규칙을 확장합니다.

### Prettier: 코드 포매터(Formatter)
**코드의 의미는 건드리지 않고 모양만 일정하게** 정리하는 도구입니다. 들여쓰기, 따옴표 종류, 세미콜론, 줄 바꿈 위치 등을 정해진 규칙대로 다시 출력합니다. 설정할 수 있는 옵션을 의도적으로 적게 두어, 팀원들이 스타일 논쟁에 시간을 쓰지 않게 합니다.

```js
// ESLint가 잡는 것: 의미상 문제
const unused = 1;              // no-unused-vars
if (value == null) {}          // eqeqeq

// Prettier가 바꾸는 것: 모양
const user={name:'kim',age:20} // -> const user = { name: 'kim', age: 20 };
```

정리하면 ESLint는 **"이 코드가 맞는가"**, Prettier는 **"이 코드가 보기 좋게 정리되어 있는가"** 를 다룹니다.

## 두 도구를 함께 사용할 때 생기는 문제와 해결 방법은 무엇인가요? 🤔

과거의 ESLint에는 들여쓰기, 따옴표 같은 **스타일 규칙**도 있어서, Prettier가 정리한 코드를 ESLint가 에러로 판단하는 **규칙 충돌**이 생길 수 있었습니다.

그래서 **`eslint-config-prettier`** 를 ESLint 설정의 마지막에 추가해, Prettier와 겹치는 ESLint의 스타일 규칙을 모두 끕니다. 그러면 **스타일은 Prettier, 코드 품질은 ESLint** 로 역할이 깔끔하게 나뉩니다. 최근 ESLint는 스타일 관련 규칙을 별도 패키지(ESLint Stylistic)로 분리하는 방향으로 바뀌어, 이런 충돌이 줄어들고 있습니다.

참고로 ESLint 9부터는 `.eslintrc` 대신 `eslint.config.js` 형식의 **Flat Config** 가 기본입니다.

## 팀에서 규칙이 지켜지도록 강제하려면 어떻게 하나요? 🧐

도구를 설치하는 것만으로는 각자 실행하지 않으면 소용이 없으므로, 여러 단계에서 자동으로 검사합니다.

1. **에디터**: 저장할 때 Prettier로 포맷하고 ESLint 경고를 바로 보여주도록 설정을 공유합니다. (`.vscode/settings.json`)
2. **커밋 전**: husky와 lint-staged로 **커밋하려는 파일에만** ESLint와 Prettier를 실행해, 규칙을 어긴 코드가 커밋되지 않게 합니다.
3. **CI**: PR마다 `eslint .`과 `prettier --check .`을 실행해, 로컬 검사를 건너뛴 경우에도 머지되지 않도록 막습니다.

또한 기존 프로젝트에 Prettier를 처음 적용하면 전체 파일이 바뀌어 `git blame`이 의미 없어지므로, 포맷 변경만 담은 커밋을 따로 만들고 `.git-blame-ignore-revs`에 등록하는 방법을 사용합니다. 최근에는 린트와 포맷을 하나의 빠른 도구로 처리하는 **Biome** 같은 대안도 쓰입니다.
