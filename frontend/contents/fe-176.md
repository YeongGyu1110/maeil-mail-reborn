**REST** 는 리소스를 URL로 표현하고, 그 리소스에 대한 행위를 HTTP 메서드(GET, POST, PUT, PATCH, DELETE)로 표현하는 **API 설계 스타일**입니다. 리소스마다 엔드포인트가 있고, **응답의 형태는 서버가 결정**합니다.

**GraphQL** 은 Meta(당시 Facebook)가 만든 **API를 위한 쿼리 언어**입니다. 보통 **하나의 엔드포인트**를 두고, 클라이언트가 **필요한 데이터의 구조를 쿼리로 직접 요청**하면 서버는 그 구조 그대로 응답합니다.

```graphql
query {
  user(id: 1) {
    name
    posts(first: 3) {
      title
    }
  }
}
```

## GraphQL은 REST의 어떤 문제를 해결하나요? 🤔

- **오버페칭(Over-fetching)**: REST의 `/users/1`은 화면에 이름만 필요해도 정해진 모든 필드를 내려줍니다. GraphQL은 요청한 필드만 받습니다.
- **언더페칭(Under-fetching)**: 사용자 정보와 게시글, 댓글을 함께 보여주려면 REST에서는 여러 엔드포인트를 차례로 호출해야 할 수 있습니다. GraphQL은 한 번의 요청으로 연관 데이터를 함께 가져옵니다.
- **강한 타입의 스키마**: API의 모든 타입이 스키마로 정의되어 있어, 이를 기반으로 **TypeScript 타입과 클라이언트 코드를 자동 생성**하고 문서처럼 탐색할 수 있습니다.
- **화면 변경에 대한 유연성**: 화면에 필드가 하나 추가되어도 백엔드 엔드포인트를 수정하지 않고 쿼리만 바꾸면 됩니다.

## 그렇다면 GraphQL의 단점은 무엇인가요? 🧐

- **HTTP 캐싱이 어렵습니다.** REST는 URL마다 리소스가 달라 브라우저, CDN의 HTTP 캐시를 그대로 활용할 수 있습니다. GraphQL은 하나의 엔드포인트에 주로 POST로 요청하므로 HTTP 캐시를 활용하기 어렵고, Apollo Client나 Relay처럼 **클라이언트 측 정규화 캐시**가 필요합니다. 쿼리를 미리 등록하고 해시로 GET 요청하는 Persisted Query로 보완하기도 합니다.
- **서버 성능 관리가 어렵습니다.** 클라이언트가 깊게 중첩된 쿼리를 보내면 서버에 큰 부하가 생길 수 있어 쿼리 깊이·복잡도 제한이 필요하고, 연관 데이터를 조회할 때 N+1 문제가 생기기 쉬워 DataLoader 같은 배칭 도구를 사용합니다.
- **에러 처리 방식이 다릅니다.** 일부 필드에서 에러가 나도 HTTP 상태는 200이고, 응답 본문의 `errors` 배열에 에러가 담기는 경우가 많습니다. 상태 코드만 보고 성공 여부를 판단할 수 없습니다.
- **학습 비용과 초기 설정 비용**이 있고, 파일 업로드처럼 표준이 아닌 기능은 별도 처리가 필요합니다.

## 어떤 기준으로 선택하시겠어요?

화면이 다양하고 데이터 관계가 복잡하며, 웹과 앱처럼 **여러 클라이언트가 서로 다른 데이터 조합을 필요로 한다면** GraphQL이 유리합니다. 반대로 리소스 구조가 단순하고, HTTP 캐싱이 중요하거나 외부에 공개하는 API라면 REST가 더 단순하고 효과적입니다. 두 방식의 중간으로, 프론트엔드에 맞춘 API를 따로 두는 **BFF(Backend For Frontend)** 를 선택하기도 합니다.
