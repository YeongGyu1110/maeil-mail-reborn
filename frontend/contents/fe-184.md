**마이크로 프론트엔드(Micro Frontends)** 는 백엔드의 마이크로서비스처럼, **하나의 큰 프론트엔드 애플리케이션을 기능 단위의 작은 애플리케이션들로 나누어 각 팀이 독립적으로 개발하고 배포**하는 아키텍처입니다. 사용자에게는 하나의 서비스처럼 보이지만, 예를 들어 쇼핑몰의 상품 검색, 장바구니, 결제를 서로 다른 팀이 각자의 저장소와 배포 일정으로 운영합니다.

서비스와 조직이 커지면 하나의 프론트엔드 저장소(모놀리스)에 수십 명이 함께 작업하게 됩니다. 그러면 빌드와 테스트가 느려지고, 한 팀의 변경 때문에 다른 팀의 배포가 막히며, 기술 스택을 바꾸기도 어렵습니다. 마이크로 프론트엔드는 이런 **조직 확장의 문제**를 해결하기 위해 등장했습니다.

## 마이크로 프론트엔드를 하나의 화면으로 합치는 방법에는 무엇이 있나요? 🤔

- **빌드 타임 통합**: 각 앱을 npm 패키지로 배포하고, 메인 앱이 의존성으로 설치해 함께 빌드합니다. 구현은 단순하지만, 하위 앱이 바뀔 때마다 메인 앱을 다시 빌드·배포해야 해서 **독립 배포라는 장점이 사라집니다.**
- **iframe**: 각 앱을 iframe으로 띄웁니다. 스타일과 자바스크립트가 완전히 격리되지만, 앱 간 통신, 라우팅, 반응형 높이 조절, 접근성, SEO 처리가 어렵습니다.
- **런타임 통합 (Module Federation)**: webpack 5에서 도입된 Module Federation으로, 각 앱이 **런타임에 다른 앱이 배포한 모듈을 원격으로 불러와** 사용합니다. 하위 앱을 배포하면 메인 앱을 다시 빌드하지 않아도 반영되고, React 같은 공통 라이브러리는 공유(shared)해 중복 로딩을 줄일 수 있습니다. 현재는 Rspack, Vite 등 여러 번들러에서도 사용할 수 있습니다.
- **Web Components**: 각 앱을 커스텀 엘리먼트로 감싸 프레임워크와 무관하게 조합합니다.
- **서버 사이드 통합**: 서버나 엣지에서 각 앱이 만든 HTML 조각을 하나의 페이지로 조합합니다.

## 마이크로 프론트엔드의 단점과 도입 시 고려할 점은 무엇인가요? 🧐

- **일관된 사용자 경험 유지**: 팀마다 따로 개발하면 버튼 모양이나 동작이 조금씩 달라지기 쉽습니다. 공통 **디자인 시스템**이 사실상 필수입니다.
- **성능 저하**: 앱마다 라이브러리를 따로 불러오면 번들이 중복되고, 여러 원격 모듈을 불러오느라 초기 로딩이 늦어질 수 있습니다. 공유 의존성의 **버전 관리**도 까다롭습니다.
- **앱 간 통신과 상태 공유**: 로그인 정보나 장바구니 개수처럼 여러 앱이 함께 쓰는 상태를 어떻게 전달할지 정해야 합니다. 앱끼리 강하게 결합되지 않도록 커스텀 이벤트나 URL처럼 느슨한 방식을 사용합니다.
- **운영 복잡도**: 저장소, 배포 파이프라인, 모니터링이 앱 수만큼 늘어나고, 런타임에 원격 모듈 하나가 실패해도 화면이 깨지지 않도록 대비해야 합니다.

따라서 마이크로 프론트엔드는 기술적인 이유보다 **여러 팀이 서로를 기다리지 않고 독립적으로 배포해야 하는 조직의 필요**가 분명할 때 도입하는 것이 좋습니다. 팀이 작다면 모노레포와 패키지 분리만으로도 충분한 경우가 많습니다.
