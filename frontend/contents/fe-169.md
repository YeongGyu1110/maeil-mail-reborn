네 가지 방식은 **HTML을 언제, 어디서 만드는지**에 따라 구분됩니다.

### CSR(Client Side Rendering)
서버는 거의 빈 HTML과 자바스크립트 번들만 내려주고, **브라우저가 자바스크립트를 실행해 화면을 만듭니다.** 첫 로딩 이후 페이지 전환이 빠르고 서버 부담이 적지만, 자바스크립트를 내려받아 실행하기 전까지 빈 화면이 보이고, 검색 엔진이 콘텐츠를 수집하기 불리합니다.

### SSR(Server Side Rendering)
**요청이 올 때마다 서버가 데이터를 조회해 HTML을 만들어** 보냅니다. 사용자는 완성된 HTML을 바로 볼 수 있어 초기 표시가 빠르고 SEO에 유리하며, 항상 최신 데이터를 보여줄 수 있습니다. 하지만 요청마다 서버 연산이 필요해 서버 비용이 들고, 데이터 조회가 느리면 첫 바이트(TTFB)가 늦어집니다.

### SSG(Static Site Generation)
**빌드 시점에 HTML을 미리 만들어** 두고, 요청이 오면 만들어 둔 파일을 그대로 응답합니다. CDN에 캐시할 수 있어 가장 빠르고 서버 부담도 거의 없습니다. 하지만 데이터가 바뀌면 다시 빌드해야 하므로, 블로그나 문서처럼 자주 바뀌지 않는 페이지에 적합합니다.

### ISR(Incremental Static Regeneration)
SSG처럼 정적 페이지를 제공하되, **정해진 시간이 지나거나 요청이 있을 때 해당 페이지만 백그라운드에서 다시 생성**합니다. 전체를 다시 빌드하지 않고도 정적 페이지를 갱신할 수 있어, 상품 목록이나 뉴스처럼 수천 개의 페이지가 있고 약간의 지연이 허용되는 경우에 적합합니다.

| | HTML 생성 시점 | 데이터 최신성 | 초기 표시 | 서버 부담 |
|---|---|---|---|---|
| CSR | 브라우저에서 실행 시 | 최신 | 느림 | 적음 |
| SSR | 요청마다 서버에서 | 최신 | 빠름 | 많음 |
| SSG | 빌드 시 | 빌드 시점 데이터 | 매우 빠름 | 거의 없음 |
| ISR | 빌드 시 + 주기적 재생성 | 일정 주기 지연 | 매우 빠름 | 적음 |

## SSR, SSG로 받은 HTML은 바로 클릭이 되나요? 🤔

아닙니다. 서버에서 만든 HTML은 **보이기만 할 뿐 이벤트 핸들러가 연결되지 않은 상태**입니다. 브라우저가 자바스크립트를 내려받아 실행하고, 이미 그려진 DOM에 이벤트 핸들러와 상태를 연결하는 **하이드레이션(Hydration)** 을 마쳐야 상호작용이 가능해집니다. 그래서 화면은 보이는데 버튼을 눌러도 반응이 없는 구간이 생길 수 있습니다. 이를 줄이기 위해 Streaming SSR, 서버 컴포넌트처럼 하이드레이션할 자바스크립트의 양과 시점을 줄이는 기술이 등장했습니다.

## 하나의 서비스에 한 가지 방식만 사용해야 하나요? 🧐

아닙니다. 최근 프레임워크는 **페이지나 컴포넌트 단위로 방식을 섞어 쓰는 것**을 전제로 합니다. 예를 들어 쇼핑몰이라면 다음처럼 나눌 수 있습니다.

- 회사 소개, 이용 약관: **SSG**
- 상품 상세: **ISR** (가격, 재고는 클라이언트에서 따로 최신 데이터를 조회)
- 검색 결과, 주문 내역: 사용자와 요청마다 결과가 달라지므로 **SSR**
- 로그인 이후의 관리자 대시보드: SEO가 필요 없으므로 **CSR**

Next.js App Router에서도 별도 설정이 없으면 빌드 시 정적으로 렌더링하고, 쿠키나 헤더처럼 요청 정보에 의존하면 동적으로 렌더링하는 식으로 라우트마다 방식이 결정됩니다. 결국 **데이터가 얼마나 자주 바뀌는지, 사용자마다 다른지, SEO가 필요한지**를 기준으로 선택합니다.
