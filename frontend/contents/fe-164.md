**React Compiler** 는 React 팀이 만든 **빌드 타임 최적화 도구**로, 컴포넌트와 훅의 코드를 분석해 **메모이제이션 코드를 자동으로 삽입**합니다. 개발자가 직접 `useMemo`, `useCallback`, `React.memo`를 작성하지 않아도, 값이 바뀌지 않았다면 계산과 리렌더링을 건너뛰도록 만들어 줍니다. 2025년에 정식(1.0) 버전이 출시되었습니다.

React는 상태가 바뀌면 해당 컴포넌트와 그 하위 컴포넌트를 다시 렌더링합니다. 그래서 그동안 불필요한 리렌더링을 막으려면 개발자가 직접 메모이제이션을 해야 했는데, 다음과 같은 문제가 있었습니다.

- 어디에 메모이제이션이 필요한지 판단하기 어렵고, 코드가 장황해집니다.
- 의존성 배열을 잘못 작성하면 오래된 값을 사용하는 버그가 생깁니다.
- 하나라도 메모이제이션이 빠지면 참조가 바뀌어 하위의 `React.memo`가 무력해집니다.

React Compiler는 **Babel 플러그인** 형태로 동작하며, 컴포넌트 안의 값들이 어떤 값에 의존하는지 분석해 **필요한 부분만 세밀하게 캐싱**합니다. 조건부 렌더링 이후의 값처럼, 사람이 `useMemo`로는 메모이제이션하기 어려운 부분까지 처리할 수 있습니다.

```jsx
// 개발자가 작성한 코드
function TodoList({ todos, filter }) {
  const visible = todos.filter((t) => t.status === filter);
  const handleClick = (id) => toggle(id);
  return <List items={visible} onClick={handleClick} />;
}
// 컴파일 후에는 todos, filter가 바뀌지 않으면
// visible, handleClick, <List />를 이전 값으로 재사용하는 코드가 생성된다
```

## React Compiler를 적용하려면 어떤 조건이 필요한가요? 🤔

컴파일러는 코드가 **React의 규칙(Rules of React)** 을 지킨다고 가정하고 최적화합니다.

- 컴포넌트와 훅은 **순수해야** 합니다. 같은 입력이면 같은 결과를 반환하고, 렌더링 중에 외부 변수를 바꾸는 등의 부수 효과가 없어야 합니다.
- props와 state는 **불변**으로 다뤄야 합니다. 직접 수정하지 않고 새 값을 만들어야 합니다.
- 훅은 **최상위에서만 호출**해야 합니다.

규칙을 어긴 컴포넌트를 만나면 컴파일러는 그 컴포넌트를 **최적화하지 않고 건너뜁니다.** 그래서 도입 전에 React Compiler 규칙이 포함된 `eslint-plugin-react-hooks`로 위반 사항을 먼저 확인하는 것이 좋습니다. 또한 디렉터리 단위로 점진적으로 적용하거나, 특정 컴포넌트에 `"use no memo"` 지시어를 넣어 제외할 수도 있습니다.

## 그렇다면 이제 useMemo와 useCallback은 필요 없나요? 🧐

새로 작성하는 코드에서는 대부분 직접 작성할 필요가 줄어듭니다. 다만 완전히 사라지는 것은 아닙니다.

- **Effect의 의존성으로 쓰이는 값**처럼, 참조가 언제 바뀌는지를 개발자가 정확히 통제해야 하는 경우에는 여전히 명시적으로 작성하기도 합니다.
- 컴파일러가 이미 적용된 코드에서 기존 `useMemo`, `useCallback`을 지우면 컴파일 결과가 달라질 수 있으므로, 충분한 테스트 없이 일괄 제거하지 않는 것이 좋습니다.

결국 React Compiler는 성능 최적화를 개발자의 수작업에서 **도구의 책임으로 옮기는 것**이며, 그만큼 개발자는 컴포넌트를 순수하게 작성하는 데 집중해야 합니다.
