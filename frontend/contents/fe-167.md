**React Testing Library(RTL)** 는 컴포넌트를 **사용자가 실제로 사용하는 방식과 최대한 비슷하게 테스트**하도록 설계된 라이브러리입니다. 컴포넌트의 state나 메서드 같은 내부 구현에 접근하는 대신, **화면에 렌더링된 결과(DOM)를 사용자처럼 찾고 조작**하도록 API를 제공합니다.

과거에 많이 쓰이던 Enzyme은 컴포넌트 인스턴스의 state를 직접 읽거나 바꿀 수 있었습니다. 하지만 이런 테스트는 사용자 입장에서는 아무 변화가 없는 리팩터링에도 깨지고, 실제 사용자 경험의 문제는 잡지 못했습니다. RTL은 이 문제를 줄이기 위해 **"사용자가 볼 수 없는 것은 테스트하지 않는다"** 는 방향을 택했습니다.

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('할 일을 추가하면 목록에 보인다', async () => {
  const user = userEvent.setup();
  render(<TodoApp />);

  await user.type(screen.getByRole('textbox', { name: '할 일' }), '장보기');
  await user.click(screen.getByRole('button', { name: '추가' }));

  expect(screen.getByRole('listitem')).toHaveTextContent('장보기');
});
```

## 요소를 찾는 쿼리는 어떤 우선순위로 사용해야 하나요? 🤔

RTL은 **사용자와 보조 기술이 요소를 인식하는 방식에 가까운 쿼리**를 우선 사용하도록 권장합니다.

1. **`getByRole`**: 역할(button, textbox, heading 등)과 접근 가능한 이름으로 찾습니다. 가장 우선적으로 사용합니다.
2. **`getByLabelText`**: 폼 요소를 label로 찾습니다.
3. **`getByPlaceholderText`**, **`getByText`**, **`getByDisplayValue`**: 화면에 보이는 텍스트로 찾습니다.
4. **`getByAltText`**, **`getByTitle`**: 이미지의 alt 등으로 찾습니다.
5. **`getByTestId`**: 위 방법으로 찾을 수 없을 때만 사용합니다. 사용자는 `data-testid`를 볼 수 없기 때문입니다.

`getByRole`로 요소를 찾을 수 없다면, 스크린 리더 사용자도 그 요소를 제대로 인식하지 못할 가능성이 높습니다. 그래서 **RTL로 테스트를 작성하는 과정 자체가 접근성을 점검하는 효과**도 있습니다.

## getBy, queryBy, findBy는 어떤 차이가 있나요? 🧐

| 쿼리 | 요소가 없을 때 | 비동기 | 사용하는 상황 |
|---|---|---|---|
| `getBy...` | 에러 발생 | X | 요소가 **있어야 하는** 경우 |
| `queryBy...` | `null` 반환 | X | 요소가 **없음을 확인**하는 경우 |
| `findBy...` | 시간 초과 시 에러 | O (Promise) | 데이터 로딩 후 **나타날** 요소를 기다리는 경우 |

```jsx
expect(screen.queryByText('에러')).not.toBeInTheDocument();
expect(await screen.findByText('kim')).toBeInTheDocument();
```

또한 이벤트는 `fireEvent`보다 **`userEvent`** 를 권장합니다. `fireEvent.click`은 click 이벤트 하나만 발생시키지만, `userEvent.click`은 실제 사용자처럼 pointerdown, mousedown, focus, mouseup, click 등을 순서대로 발생시켜 더 현실적인 상호작용을 재현합니다.
