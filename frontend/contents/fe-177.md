**HTTP/3** 는 HTTP의 세 번째 메이저 버전으로, 가장 큰 변화는 **전송 계층을 TCP에서 UDP 기반의 QUIC 프로토콜로 바꾼 것**입니다. HTTP의 의미(메서드, 상태 코드, 헤더)는 그대로이고, 데이터를 실어 나르는 방식이 바뀌었습니다.

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | **QUIC (UDP 기반)** |
| 다중화 | 연결당 한 번에 하나의 요청 | 하나의 연결에서 여러 스트림 | 하나의 연결에서 **독립적인** 여러 스트림 |
| 암호화 | 선택 (TLS) | 사실상 TLS 필수 | **QUIC에 TLS 1.3 내장** |
| HOL 블로킹 | HTTP 계층에서 발생 | TCP 계층에서 발생 | 스트림 단위로 격리 |

## HTTP/2에도 다중화가 있는데, 왜 HTTP/3가 필요했나요? 🤔

HTTP/2는 하나의 TCP 연결에서 여러 요청을 동시에 주고받아 **HTTP 계층의 HOL(Head-of-Line) 블로킹** 을 해결했습니다. 하지만 TCP는 모든 데이터를 **하나의 순서 있는 바이트 흐름**으로 다룹니다. 그래서 패킷 하나가 유실되면, 그 패킷과 관계없는 다른 스트림의 데이터까지 **유실된 패킷이 재전송될 때까지 모두 대기**합니다. 이것을 **TCP 계층의 HOL 블로킹** 이라고 하며, 패킷 손실이 잦은 모바일 네트워크에서 특히 문제가 됩니다.

QUIC는 스트림을 전송 계층에서 직접 관리하므로, **한 스트림의 패킷이 유실되어도 다른 스트림은 계속 전달**됩니다.

## HTTP/3의 다른 장점은 무엇인가요? 🧐

- **빠른 연결 수립**: 기존에는 TCP 핸드셰이크 후 TLS 핸드셰이크를 따로 해야 했습니다. QUIC는 연결 수립과 TLS 1.3 핸드셰이크를 합쳐 **1-RTT** 만에 연결하고, 이전에 연결한 적 있는 서버라면 **0-RTT** 로 첫 요청부터 데이터를 보낼 수 있습니다. (단, 0-RTT 데이터는 재전송 공격에 취약해 멱등한 요청에만 사용해야 합니다.)
- **연결 이전(Connection Migration)**: TCP 연결은 IP와 포트로 식별되어, Wi-Fi에서 LTE로 바뀌면 연결이 끊어집니다. QUIC는 **연결 ID** 로 연결을 식별해 네트워크가 바뀌어도 연결을 유지할 수 있습니다.
- **빠른 개선**: TCP는 운영체제 커널에 구현되어 바꾸기 어렵지만, QUIC는 사용자 영역(애플리케이션)에서 구현되어 프로토콜 개선을 더 빠르게 적용할 수 있습니다.

## 브라우저는 서버가 HTTP/3를 지원하는지 어떻게 알 수 있나요?

보통 처음에는 HTTP/1.1이나 HTTP/2로 연결하고, 서버가 응답의 **`Alt-Svc` 헤더**(예: `Alt-Svc: h3=":443"`)로 HTTP/3를 지원한다고 알리면, 다음 요청부터 HTTP/3로 연결합니다. DNS의 HTTPS 레코드로 미리 알리는 방법도 있습니다. 일부 네트워크는 UDP 트래픽을 막기도 하므로, 브라우저는 HTTP/3 연결에 실패하면 HTTP/2로 되돌아갑니다(fallback).

프론트엔드 개발자가 코드를 바꿀 필요는 없지만, 대부분의 CDN이 HTTP/3를 지원하므로 **CDN 설정에서 활성화하는 것만으로** 모바일 사용자의 로딩 성능을 개선할 수 있습니다. 개발자 도구 Network 탭의 Protocol 열에서 `h3`로 확인할 수 있습니다.
