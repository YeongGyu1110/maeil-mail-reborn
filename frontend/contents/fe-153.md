HTTP는 기본적으로 **클라이언트가 요청해야만 서버가 응답하는 구조**입니다. 그래서 채팅, 알림, 주식 시세처럼 서버의 변화를 바로 받아야 하는 기능은 별도의 방법이 필요합니다. 대표적으로 **폴링, 롱 폴링, SSE, WebSocket** 이 있습니다.

### 폴링(Polling)
클라이언트가 **일정 주기마다 서버에 요청**을 보내 새 데이터가 있는지 확인합니다. 구현이 가장 단순하지만, 변화가 없어도 계속 요청을 보내므로 자원이 낭비되고, 주기만큼 지연이 생깁니다.

### 롱 폴링(Long Polling)
클라이언트가 요청을 보내면 서버는 **새 데이터가 생길 때까지 응답을 미뤘다가** 데이터가 생기면 응답합니다. 클라이언트는 응답을 받자마자 다시 요청을 보냅니다. 폴링보다 지연과 불필요한 요청이 줄지만, 이벤트가 잦으면 요청-응답이 계속 반복되고 서버가 열린 연결을 오래 유지해야 합니다.

### SSE(Server-Sent Events)
하나의 HTTP 연결을 열어 두고 **서버가 클라이언트로 이벤트를 계속 흘려보내는 단방향 통신**입니다. 응답의 `Content-Type`은 `text/event-stream`이고, 브라우저에서는 `EventSource` API로 사용합니다. 연결이 끊기면 브라우저가 **자동으로 재연결**하고, 일반 HTTP 위에서 동작해 기존 인프라와 잘 맞습니다. 알림, 피드 갱신, LLM 응답 스트리밍처럼 서버에서 클라이언트로만 데이터가 흐르는 경우에 적합합니다.

### WebSocket
HTTP 요청으로 시작해 `Upgrade` 헤더로 프로토콜을 전환(`101 Switching Protocols`)한 뒤, **하나의 TCP 연결 위에서 양방향(full-duplex) 통신**을 합니다. `ws://`, `wss://` 스킴을 사용하며, 헤더 오버헤드가 작아 채팅, 협업 편집, 멀티플레이 게임처럼 양쪽이 자주 메시지를 주고받는 경우에 적합합니다. 다만 재연결, 하트비트(ping/pong), 메시지 순서 보장 등을 직접 처리해야 하고, 서버가 연결 상태를 유지해야 해 확장 시 고려할 점이 많습니다.

| | 방향 | 연결 | 재연결 | 적합한 예 |
|---|---|---|---|---|
| 폴링 | 클라이언트 → 서버 | 매번 새 요청 | 불필요 | 갱신이 드문 대시보드 |
| 롱 폴링 | 클라이언트 → 서버 | 응답마다 새 요청 | 직접 구현 | 레거시 환경의 알림 |
| SSE | 서버 → 클라이언트 | HTTP 연결 유지 | 브라우저 자동 | 알림, 스트리밍 응답 |
| WebSocket | 양방향 | 별도 프로토콜로 연결 유지 | 직접 구현 | 채팅, 협업 툴 |

## SSE를 사용할 때 주의할 점이 있나요? 🤔

HTTP/1.1에서는 브라우저가 **도메인당 동시 연결 수를 약 6개로 제한**합니다. SSE 연결은 계속 열려 있으므로, 여러 탭에서 SSE를 열면 다른 요청이 막힐 수 있습니다. HTTP/2 이상에서는 하나의 연결에서 여러 스트림을 다중화하므로 이 문제가 크게 줄어듭니다.

또한 `EventSource`는 **GET 요청만 보낼 수 있고 커스텀 헤더를 설정할 수 없어**, `Authorization` 헤더로 토큰을 보내기 어렵습니다. 이 경우 쿠키 기반 인증을 사용하거나, `fetch`로 스트림을 직접 읽는 방식을 사용합니다.

## 어떤 기준으로 방식을 선택하시겠어요? 🧐

먼저 **데이터가 흐르는 방향**을 봅니다. 서버에서 클라이언트로만 보내면 된다면 구현과 운영이 단순한 SSE를, 클라이언트도 실시간으로 자주 보내야 한다면 WebSocket을 고려합니다. 갱신 주기가 길고 약간의 지연이 괜찮다면 폴링만으로도 충분합니다. 실시간성이 꼭 필요하지 않은데 WebSocket을 도입하면 서버 확장과 장애 대응 비용만 늘어날 수 있습니다.
