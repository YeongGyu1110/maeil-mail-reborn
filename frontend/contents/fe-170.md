Context API는 props를 여러 단계로 내려 보내는 **props drilling 없이 컴포넌트 트리에 값을 공유**하는 기능입니다. 하지만 상태 관리 도구로 사용할 때는 **리렌더링 범위**를 주의해야 합니다.

Context의 값이 바뀌면, React는 **그 Context를 구독(`useContext`)하는 모든 컴포넌트를 다시 렌더링**합니다. 컴포넌트가 값의 일부만 사용하더라도 마찬가지입니다.

```jsx
const AppContext = createContext(null);

function AppProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');

  // 렌더링마다 새 객체가 만들어진다
  return (
    <AppContext.Provider value={{ user, setUser, theme, setTheme }}>
      {children}
    </AppContext.Provider>
  );
}

function ThemeButton() {
  const { theme, setTheme } = useContext(AppContext);
  // user만 바뀌어도 이 컴포넌트가 다시 렌더링된다
}
```

여기에는 두 가지 문제가 있습니다.

1. **선택적으로 구독할 수 없습니다.** `theme`만 쓰는 컴포넌트도 `user`가 바뀌면 리렌더링됩니다.
2. **`value`에 매번 새 객체를 넘기면**, Provider의 부모가 리렌더링될 때 값이 실제로는 같아도 참조가 바뀌어 모든 구독 컴포넌트가 리렌더링됩니다.

## 이 문제를 어떻게 해결할 수 있나요? 🤔

- **value 메모이제이션**: `useMemo`로 `value` 객체를 감싸 실제 값이 바뀔 때만 새 객체가 되게 합니다.
- **Context 분리**: 함께 바뀌지 않는 값은 Context를 나눕니다. `UserContext`와 `ThemeContext`로 나누거나, 자주 바뀌는 **상태**와 거의 바뀌지 않는 **업데이트 함수**를 각각 다른 Context로 제공하면, 업데이트 함수만 쓰는 컴포넌트는 상태 변경에 리렌더링되지 않습니다.
- **상태를 필요한 곳 가까이 두기**: 일부 하위 트리에서만 쓰는 상태라면 Provider를 그 하위 트리에만 두어 영향 범위를 줄입니다.
- **`children` 활용**: Provider 컴포넌트가 `children`을 받아 렌더링하면, Provider의 상태가 바뀌어도 `children`으로 전달된 요소는 다시 만들어지지 않아 구독하지 않는 컴포넌트는 리렌더링되지 않습니다.

## 그렇다면 언제 Context 대신 상태 관리 라이브러리를 사용해야 하나요? 🧐

Context는 본래 **상태 관리 도구라기보다 값을 전달하는(dependency injection) 도구**에 가깝습니다. 테마, 언어, 로그인 사용자처럼 **자주 바뀌지 않고 여러 곳에서 읽는 값**에 적합합니다.

반면 값이 자주 바뀌고, 많은 컴포넌트가 상태의 서로 다른 일부만 구독해야 한다면 Zustand, Jotai, Redux 같은 라이브러리를 고려합니다. 이 라이브러리들은 `useSyncExternalStore`를 기반으로 **선택자(selector)로 필요한 값만 구독**할 수 있어, 해당 값이 바뀔 때만 컴포넌트가 리렌더링됩니다.

```js
const theme = useStore((state) => state.theme); // theme이 바뀔 때만 리렌더링
```

또한 서버에서 받아온 데이터라면 Context에 담기보다 TanStack Query 같은 서버 상태 관리 도구로 캐싱하는 것이 일반적입니다.
