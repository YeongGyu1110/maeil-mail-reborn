인증 토큰을 어디에 저장할지는 **XSS와 CSRF 중 어떤 공격에 더 대비할지의 트레이드오프**입니다. 정답이 하나로 정해져 있지는 않지만, 널리 쓰이는 방식은 **Access Token은 메모리에, Refresh Token은 `HttpOnly` 쿠키에 저장**하는 것입니다.

### localStorage / sessionStorage
자바스크립트로 쉽게 읽고 쓸 수 있고, 요청에 자동으로 포함되지 않아 CSRF에는 안전합니다. 하지만 **같은 페이지에서 실행되는 모든 스크립트가 읽을 수 있어**, XSS 취약점이나 오염된 서드파티 스크립트가 있으면 토큰이 그대로 탈취됩니다.

### HttpOnly 쿠키
`HttpOnly` 속성을 주면 **자바스크립트에서 쿠키를 읽을 수 없어** XSS로 토큰 값을 빼가기 어렵습니다. 대신 브라우저가 요청마다 쿠키를 **자동으로 포함**하므로 CSRF에 대비해야 합니다. 이때 `SameSite` 속성과 CSRF 토큰을 함께 사용합니다.

### 메모리(자바스크립트 변수)
새로고침하면 사라지므로 탈취되더라도 노출 시간이 짧고, 저장소에 남지 않습니다. 대신 새로고침이나 새 탭에서 다시 받아와야 합니다.

## Access Token과 Refresh Token은 왜 나누나요? 🤔

토큰 기반 인증은 서버가 상태를 저장하지 않아서 **한 번 발급한 토큰을 중간에 무효화하기 어렵습니다.** 그래서 API 호출에 쓰는 **Access Token은 수명을 짧게(예: 수 분~수십 분)** 두어 탈취되더라도 피해 시간을 줄이고, 새 Access Token을 받는 데만 쓰는 **Refresh Token은 수명을 길게** 두어 사용자가 자주 로그인하지 않아도 되게 합니다.

이를 조합하면 다음과 같은 흐름이 됩니다.

1. 로그인하면 서버가 Access Token은 응답 본문으로, Refresh Token은 `HttpOnly; Secure; SameSite` 쿠키로 내려줍니다.
2. 클라이언트는 Access Token을 메모리에 두고 `Authorization: Bearer` 헤더로 API를 호출합니다.
3. Access Token이 만료되어 401 응답을 받으면, 쿠키가 자동으로 포함되는 재발급 API를 호출해 새 Access Token을 받고 원래 요청을 다시 보냅니다.
4. 새로고침 시에도 같은 재발급 API로 로그인 상태를 복원합니다.

추가로 Refresh Token을 쓸 때마다 새 것으로 교체하는 **Refresh Token Rotation** 을 적용하면, 이미 사용된 Refresh Token이 다시 들어왔을 때 탈취를 감지하고 해당 사용자의 토큰을 모두 무효화할 수 있습니다.

## SameSite 쿠키 속성에 대해 설명해주세요. 🧐

`SameSite`는 **다른 사이트에서 시작된 요청에 쿠키를 보낼지**를 정하는 속성입니다.

- `Strict`: 같은 사이트에서 시작된 요청에만 쿠키를 보냅니다. 외부 링크를 클릭해 들어와도 쿠키가 빠져 로그인이 풀린 것처럼 보일 수 있습니다.
- `Lax`: 다른 사이트에서 오는 요청 중 **최상위 이동(링크 클릭 등)의 GET 요청**에만 쿠키를 보냅니다. 다른 사이트에서 보내는 POST 폼 제출이나 `fetch` 요청에는 쿠키를 보내지 않아 대부분의 CSRF를 막을 수 있습니다. 최신 Chrome 등은 속성이 없으면 `Lax`처럼 취급합니다.
- `None`: 다른 사이트 요청에도 쿠키를 보냅니다. 반드시 `Secure`와 함께 써야 합니다.

프론트엔드와 API 서버의 도메인이 다를 때는 `credentials: 'include'` 설정과 서버의 CORS 설정(`Access-Control-Allow-Credentials`)도 함께 맞춰야 쿠키가 전달됩니다.
